# VESC 零指令使能后断链分析

## 执行范围

读取并保存现有现场日志，检查按钮、串口和恢复代码，离线检查日志中的接收字节。桌面自动化服务三次返回 native pipe 不存在；本轮没有自动点击、使能或启动电机，也没有修改运行程序。

|---|---|---|

| 遥测超过 500 ms 未更新 | 21:52:07.160 | 21:52:11.690 |

这两次记录与早先 SerialStream.EndWrite 抛出 OperationCanceledException 不同。超时时仍有接收和发送活动。原连接恢复后，软件依然关闭并重开串口，disconnect_start 的 failure 为空。

## 已确认的软件行为

MainViewModel.RecordVescDiagnostic 收到 vesc_telemetry_stale 后立即启动 RecoverDutLinkAsync。后者停止负载，等待，随后无条件调用 ConnectDutAsync；没有在重新连接前确认原链路是否已恢复。因此短暂遥测异常会引发后续额外的断开重连。

零指令使能路径通过 BenchRuntime.Enable、EtherCatDirectBridge.WriteCommandAsync 向 EtherCAT 服务发送 enable_torque 和零转矩指令。检查到的直接调用链没有关闭 COM4 或取消 VESC 通信任务。

## 接收字节检查

对两条 stale 日志各自保存的 256 字节 recentRxHex 离线检查：查找 02 49 04 开头的 COMM_GET_VALUES 候选帧，按声明长度 73 字节检查帧尾和 CRC16。第一条有三个完整候选，第二条有两个完整候选，均未通过完整帧校验。另有尾部不完整候选，不能用于判断错误。

这说明有字节进入接收路径但这些候选并非有效遥测帧。快照只有 256 字节，不能单凭它确定错误发生在硬件传输、USB/驱动、接收缓冲还是协议处理，也不能确定整个超时窗口没有其他有效帧。

## 结论和剩余工作

已确认恢复流程会在原连接恢复后仍主动断开。这个软件行为解释了部分可见断链，但不能解释最初的坏帧或早先的底层写入异常。换线无效不能单独排除主控、供电或干扰。

下一次实际复现需要桌面控制服务恢复。应同步记录单次串口读写的时间、字节内容、CRC/重同步计数、异常 HResult、任务取消状态以及伺服使能事件；保留停机保护。之后再决定修复，避免仅延长超时或吞掉异常。

## 继续排查：软件内部验证

### 原始解析器离线回放

建立 `MSLB/tmp/vesc-analysis/Replay.csproj`，直接编译引用当前 VescProtocol.cs；测试不打开串口，不操作电机。

- 取 7 条现场 stale 日志的 recentRxHex，每条追加一帧已知有效遥测，按 1 到 128 字节分块输入原始解析器，共 896 组检查全部通过。
- 21:52 两段原始快照各自解析出 0 个有效帧；追加有效帧后均能恢复。未复现当前解析器因这些片段而永久卡住或因正常分包丢帧。
- 通过反射载入启动脚本所指向的 app-v142/MotorLoadBench.Infrastructure.dll，分别将这 7 段片段加有效帧整体输入发布版解析器；7 次也都成功恢复。因此文件日期不同不能据此认定版本差异就是根因。尚未确认现场进程实际加载的路径。
- 实测释放设置了 CancelAfter 的连接 CTS 后，关联的工作 CTS 不会因此自动取消。当前 UI 使用 using 释放连接超时 CTS，不能据此推断 8 秒后必然断链。

### 已发现但需区分因果的代码问题

1. WorkerAsync 先检查遥测年龄，再读取 BytesToRead；如果线程延迟调度且缓冲区已有新数据，仍可能先触发 stale 和恢复流程。21:52 的现场记录分别有 39 和 63 字节待读，但现有日志没有记录这些待读字节的有效性，不能证明这两次一定是误报。
2. 发送与读取共用同一个循环，同步 port.Write 位于读取之前，WriteTimeout 为 1000 ms，比 500 ms 遥测阈值长。写入阻塞会连带推迟读取；这是结构性风险，并不能解释早先仅距正常遥测几十毫秒的底层写异常。
3. 连接/断开没有整体互斥，旧工作任务关闭等待有上限，任务读取共享 _port 字段。这是并发重连时的竞态风险；日志中首次故障前没有对应 connect/disconnect 事件，尚不能作为首次故障原因。
4. 自动恢复没有在重连前检查原链路是否恢复；最新两次日志直接证明这个问题发生。
5. CaptureServoEnableVescAsync 允许断链后等待恢复，且自动恢复会失能伺服，最后却仍可记为“60s telemetry continuous / remained healthy”。此诊断 PASS 不能证明伺服连续使能 60 秒且全程通信无中断。

### 字节层补充证据

21:52:11 的快照里一个相邻 02 49 04 候选头之间的片段只有 77 字节，协议声明应为 78 字节。尝试在其负载内插入单个 00，可得到一个唯一字节序列通过 CRC 校验。这与缺失一个零字节相符；这只是离线诊断重建，绝不能用重建数据作为控制遥测。其他片段未通过单段补零法恢复。

recentRx 在 TryTakeFrame 调用前从 SerialPort.Read 返回值复制，所以解析器本身不能改变已记录的 recentRx。下一步必须在 SerialPort.Read 边界记录每次返回数据及 SerialError/底层错误，才能判断字节缺失发生在读取前、驱动层还是连接生命周期竞态。现有证据不足以宣称首次异常已完全锁定到上位机业务代码。

## 2026-09-26 软件修正

- VescBridge 每轮先清空并解析驱动接收缓冲，再判断遥测是否过期；发送遥测请求后再次清空缓冲。
- 小型控制帧写超时由 1000 ms 限制为 `min(200 ms, staleAfterMs)`，避免一次同步写入阻塞超过整个遥测健康窗口。
- 新增 `vesc_write_failed`，记录命令 ID、写入耗时、CancellationToken 状态、HResult 和完整异常。
- stale/worker failure 触发恢复后先等待 300 ms 复查；原链路已恢复时记录 `vesc_recovery_cancelled`，不停止伺服、不关闭 COM4。
- 连续稳定诊断一旦检测到通信中断，即使之后自动恢复也判失败，不再输出误导性的连续 60 秒 PASS。
- 发布至 `artifacts/app-v143`，run.cmd 和 run.ps1 已切换到此版本。
